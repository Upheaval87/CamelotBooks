1.1 REV 2 SCHEMA ADDITIONS:
  accounts.version INT DEF 0 — optimistic-locking column (§1.4 below).
  coa_audit_trail(id, user_id, acted_at, account_id FK, action
  [CREATE|EDIT|DEACTIVATE|REACTIVATE|SET_CONTROLLED|UNSET_CONTROLLED], field, old_value,
  new_value, reason NULL, ip, device) — the single audit table for every account
  lifecycle change referenced across §5 and §7's "all lifecycle changes audited."
  account_type_code_ranges(account_type, sub_type NULL, range_start, range_end) —
  OPTIONAL, only if Stage 1 discovery confirms the existing system enforces a numeric
  code convention (as the mockup's 1000s/2000s/etc. pattern implies); if the system has
  no such convention today, document that decision instead of inventing ranges.

1.2 REV 2 — POSTING RULE FOR CONTROL ACCOUNTS: confirm, from the existing GL posting
handler (read-only discovery, do not modify it), whether an account with is_control=true
can itself receive direct postings, or whether postings must always target a leaf
account. Document the decision. This determines how §2.2's roll-up is validated: if
control accounts can carry their own balance in addition to children's roll-up, the
roll-up sum must include the control account's own balance as a line, not just its
children's — state which model applies and keep tree/list consistent with it.

1.3 REV 2 — PARENT / TYPE CONSISTENCY: on create or edit, reject a parent_id assignment
where the child's account_type/sub_type is inconsistent with the parent's, and reject any
parent_id chain that would create a cycle. This validation lives with the shared roll-up/
account-write logic (Stage 2), not duplicated per screen.

1.4 REV 2 — RECLASSIFICATION GUARD: changing account_type, sub_type, or parent_id on an
account that has any posted GL activity is blocked by default (422, clear message)
because it would retroactively change how prior, already-reported periods are
classified. If the business genuinely needs to reclassify an account with history,
that requires an explicit, separately-approved migration path outside this page's normal
edit flow — do not silently allow it through the standard Edit Account action.

1.5 REV 2 — CONCURRENCY: accounts.version supports optimistic locking on edit/
deactivate/reactivate. The client submits the version it loaded; if the account was
modified by someone else since, the write is rejected with a "this account was just
updated, please refresh" error rather than silently overwriting the other change.

==================== 2 · HIERARCHY + ROLL-UPS ====================
2.1 Tree derived as Type → Sub-type (grouped from account_type+sub_type) → Control
(is_control or has children) → Sub (parent_id set). Group nodes are virtual (not rows).
2.2 Roll-up: node.opening/Σ = Σ descendant leaf opening; same for current; contra values
negative; API GET /api/coa/tree returns nested nodes with rolled figures + counts;
cached, invalidated on posting/account change.
2.3 Equation strip: Total Assets vs Liabilities+Equity from rolled currents; ✓ Balanced
or red ⚠ with difference; imbalance blocks PDF/Excel export.
2.4 REV 2 — SHARED ROLL-UP FUNCTION: the tree's node roll-ups (§2.2) and the list view's
per-section totals (APPENDIX A's `.sec-h .tot`) MUST call the same underlying roll-up
function against the same data — never two independently-computed sums that could drift
apart. Verify this by construction (one function, two callers), not just by comparing
output.
2.5 REV 2 — OPENING VS CURRENT BALANCE: "Opening" in the tree/list columns is the
account's stored accounts.opening_balance (a one-time inception value, per §1), NOT a
period-relative opening balance — this page has no date/period selector, so "Current" is
computed from all posted GL activity as of now (per the posted-only rule implied by
§HARD GUARD). If the business actually needs a period-relative Opening column (i.e. prior
period's closing balance), that is a different feature (a Trial Balance report) and out
of scope for this page — state which interpretation was implemented in the final REPORT
so this isn't left ambiguous.

==================== 4.5 · CREATE / EDIT ACCOUNT (REV 2 — NEW) ====================
The "＋ New Account" and "✎ Edit account" actions visible in APPENDIX A have no backing
spec in the original document — this section defines them.

4.5.1 CREATE: POST /api/accounts {code, name, description?, account_type, sub_type?,
parent_id?, is_control?, is_contra?, opening_balance?}
  Validation: code unique (409 if taken); code within the applicable range if
  account_type_code_ranges is in use (§1.1) — else no range check, per the documented
  decision; account_type required; parent/type consistency per §1.3; parent cycle check
  per §1.3; is_controlled is NEVER settable via this endpoint (§7.1 covers that
  separately). On success: insert row, write coa_audit_trail CREATE row, invalidate
  roll-up cache (§2.2), return the new node for immediate tree/list insertion.

4.5.2 EDIT: PATCH /api/accounts/{id} {name?, description?, sub_type?, parent_id?,
opening_balance?, ...}
  IMMUTABLE once created: code (never editable — create a new account instead), and
  account_type (never editable directly — see §1.4 reclassification guard for the rare
  exception path). parent_id / sub_type changes are subject to §1.4's reclassification
  guard (blocked if the account has posted activity). is_controlled accounts (§6) reject
  all edits except by System Admin via the §7.1 controlled-flag path. Every successful
  edit writes a coa_audit_trail EDIT row per changed field (old→new).

==================== 5 · GUARDED DEACTIVATE / REACTIVATE API ====================
POST /api/accounts/{id}/deactivate {reason}
  403 without accounts.deactivate; 422 if is_controlled; 422 if current_balance ≠ 0;
  422 if activity in any OPEN period; 422 if referenced by unposted transactions;
  else status→inactive + audit row (old→new, reason, ip/device, user).
POST /api/accounts/{id}/reactivate → status→active + audit.
UI: row ⋯ menu → Deactivate (modal, mandatory reason) / Reactivate; controlled rows show
🔒 and disabled menu item; list + tree chips update (Active/Inactive/Controlled).
5.6 REV 2 — DEACTIVATE GUARD ADDITION: also 422 if the account is referenced by any
active recurring journal template, budget line, or scheduled transaction (reuse existing
scheduling/template infrastructure to check this — do not build a new one).
5.7 REV 2 — REACTIVATE GUARDS: reactivating a leaf/child account whose parent (control)
account is currently inactive is blocked with a clear message directing the user to
reactivate the parent first — do not allow an active account to exist under an inactive
parent. Reactivating a control account does NOT automatically reactivate its inactive
children (each is reactivated individually, preserving intentional per-account history).
