# Build: Bank Reconciliation module (replaces existing feature) — attach to Banking nav

## Objective
There is already a **basic Bank Reconciliation feature** in the app today, but it is not
comprehensive enough (no matching engine, no import/normalization, no audit trail, no
locking). You are to **remove that existing feature entirely first** (§0), then build a
brand-new **Bank Reconciliation module** — not a report, a controlled workflow — in its place,
attached as an item under the existing **Banking** nav section. The module proves that the
bank statement balance agrees with the accounting system's book balance, after accounting for
legitimate timing differences and errors, through an auditable, lockable process.

## Non-negotiable design principle
**Never let the user simply type a "reconciled balance" and save.** The system must calculate
the book/bank position from underlying transactions at every step. The statement's *closing
balance* is the one value entered by the user (because it comes from the physical bank
statement), but every other balance — adjusted bank balance, adjusted book balance, the
Difference — is always computed by the system from real transaction and adjustment data, never
typed in directly.

Build this as a layered workflow, not a CRUD screen:
- **Layer 1 — Import**: bank statement → system (raw statement lines, normalized).
- **Layer 2 — Matching**: bank transactions ↔ accounting transactions (auto + manual, one-to-one, one-to-many, many-to-one).
- **Layer 3 — Resolution**: unmatched items → match / create / adjust / investigate.
- **Layer 4 — Control**: validate → approve (optional) → complete → lock.

Keep the **reconciliation engine separate from the UI**, as its own service/module layer:
```
Bank Statement Import → Transaction Normalization → Matching Engine → Adjustment Engine → Reconciliation Ledger → Audit Trail
```
This lets you add more bank statement formats later (OFX, MT940, CAMT.053) without touching
core accounting/matching logic. Do not hardcode format-specific parsing into UI controllers —
route all imports through a normalization step that outputs a common internal transaction shape.

## 2 · Data model (build if it doesn't already exist)
At minimum, model:
- **Reconciliation** — bank account (FK to existing bank/cash account), statement date, statement number, opening balance, closing balance (as entered from the statement), currency, status, created/approved/completed/reversed audit fields (see §7), links to its statement lines, matches, and adjustments.
- **Bank Statement Line** — the normalized import of one statement row: date, reference, description, debit/credit amount, running balance (if provided), source file, raw/original column values (for traceability), status (`bank-only`, `matched`, `adjusted`, `ignored`).
- **Book Transaction reference** — not a new ledger entity; reference existing GL/cash transactions, plus a reconciliation-scoped status (`matched`, `outstanding`, `unmatched`, `book-only`).
- **Match** — links one-or-many bank statement lines to one-or-many book transactions, match method (`auto-exact`, `auto-likely`, `manual`), confidence score where applicable, matched-by/matched-at.
- **Adjustment** — type (from the controlled list in §6), amount, date, GL account, description, tax treatment where relevant, the accounting entry it created, created-by/at.
- **Audit Log** — append-only log of every material action taken within a reconciliation (created, imported, auto-matched, manually matched, unmatched, adjustment added, transaction created, validated, approved, completed, reversed), each with actor, timestamp, and a human-readable description (see the Audit Trail pane in §5.4 for the expected format).

## 3 · Status vocabulary (use exactly these, don't invent synonyms)
**Reconciliation status:** `Draft` → `In Progress` → `Ready for Review` → `Approved` (optional step) → `Reconciled` (locked). Plus `Reversed` as a terminal state reachable only from `Reconciled`.
**Line/transaction status (within a reconciliation):** `Matched`, `Unmatched`, `Outstanding`, `Pending`, `Bank-only`, `Book-only`, `Adjusted`, `Reconciled`.
**Register badges (dashboard list):** 🟢 Reconciled · 🟡 In Progress · 🔴 Difference · ⚪ Draft — map these to reconciliation status + whether Difference = 0.

## 4 · Core workflow rules
1. **Creating a reconciliation** asks for bank account, statement date, statement number, opening balance, closing balance (from the real statement), currency. Nothing else is typed as a "final" balance — everything downstream is computed.
2. **Import** supports **CSV and Excel now** (build the parser + normalization step for these two). Architect the import layer so OFX, QFX, MT940, and CAMT.053 can be added later as additional parsers feeding the same normalization step — do not build format support directly into UI or controller code. After parsing, show a **column-mapping screen** (§5.3) so the user can map the bank's actual column headers (which vary by bank — "Transaction Date" vs "Value Date", etc.) to the system's canonical fields (Date, Reference, Description, Debit/Withdrawal, Credit/Deposit, Balance). Never assume a fixed column layout.
3. **Auto matching** searches for matches using amount, date (± a configurable tolerance), reference, transaction number, description, bank reference, and payee. Produce a confidence score per candidate match (e.g. "Exact Match — 100%", "Likely Match — 94%") and require explicit user confirmation before finalizing any auto-suggested match (the mockup's confirmation bar in §5.4 — Confirm / Skip).
4. **Manual matching**: user selects one bank line + one book transaction and matches them explicitly ("Match Selected").
5. **One-to-many / many-to-one matching**: support one bank transaction matching multiple book transactions ("Match Multiple") and multiple bank transactions matching one book transaction ("Group & Match"), with the matched group's total required to equal within the matched amount (flag if it doesn't).
6. **Unmatched bank-only items** (e.g. a bank charge with no system record) are resolved via **Create Transaction** (§5.5): creates the real accounting entry (through the app's existing entry-posting mechanism) *and* matches it to the statement line in one step — never by silently editing the statement.
7. **Unmatched book-only items** (e.g. a payment the bank hasn't cleared yet) are **never deleted** — mark them `Outstanding` and carry them into the reconciliation calculation as a timing difference.
8. **Adjustments** ("Add Adjustment") are limited to a controlled type list: Bank charges, Interest received, Direct debit, Bank interest, Bank error, Accounting error, Returned cheque, Dishonoured payment, Deposit in transit, Outstanding cheque. Where a type requires an accounting entry (e.g. bank charges, interest received), create it through the existing posting mechanism, not as a cosmetic note.
9. **Reconciliation calculation** must be computed, shown, and internally consistent — e.g.:
   ```
   Bank statement balance
   + Deposits in transit
   − Outstanding cheques/payments
   = Adjusted bank balance

   Book balance
   ± pending adjustments (bank charges, interest, etc.)
   = Adjusted book balance

   Difference = Adjusted bank balance − Adjusted book balance
   ```
   The methodology must be consistent and auditable — don't switch calculation direction between screens.
10. **Difference must be prominently displayed everywhere relevant** (dashboard KPI, workspace calculation card). If Difference ≠ 0, **block** "Complete Reconciliation" (disabled button) and show a clear warning naming the remaining difference and, where determinable, its likely cause (e.g. "unrecorded bank charge"). Only when Difference = 0 does completion unlock.
11. **Completion locks the reconciliation.** Once `Reconciled`, it cannot be deleted. The only path forward is **Reverse Reconciliation**, which requires a reason, records the user and timestamp, and — if the org has approval workflow enabled — requires approval. This must write to the audit log.
12. **Optional approval workflow, controlled by a user-facing toggle**: build a setting (e.g. under this module's or the app's existing settings area) that turns the approval step on/off — the user will decide the on/off state themselves; do not hardcode it to either state as a default assumption baked into the workflow logic. When the toggle is ON: `Draft → In Progress → Ready for Review → Approved → Reconciled`, with configurable approver roles (e.g. Accountant → Supervisor → Finance Manager). When OFF: `Ready for Review → Reconciled` skips the Approved step. Build this as a single configurable code path branching on the toggle's live value, not two parallel implementations — so flipping the toggle immediately changes behavior for all subsequent reconciliations without a redeploy. Make sure the toggle itself is easy to find (expose it clearly in this module's settings, and mention its exact location in your final report).
13. **Audit trail is mandatory** for every reconciliation: created by/at, imported by/at, matched by/at (per match), approved by/at (if applicable), completed by/at, reversed by/at (if applicable), plus a running log of every match/unmatch/adjustment/create-transaction action in the human-readable format shown in §5.4.
