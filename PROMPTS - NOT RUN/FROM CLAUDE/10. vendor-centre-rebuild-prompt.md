# Vendor Centre module — FULL REMOVAL of existing feature, then FULL REBUILD to exact design

## Objective
There is already a Vendor Centre feature in the app today, but it is not comprehensive
enough. You are to **remove that existing feature entirely first** (§0), then **rebuild it
from scratch** as the complete supplier workspace: vendor information, transactions, bills,
payments, documents and performance — tightly integrated with Accounts Payable,
Purchasing/Inventory, General Ledger, Banking, Tax and the Reporting engine. Match the exact
markup/CSS given in §3 below, wired to real data and real workflow logic (§2).

This is not a re-skin of the current pages; treat it as tearing out the old implementation and
building a new one that happens to reuse the same underlying accounting concepts (AP balances,
approvals, GL posting, aging, credit limits).

**Note on rails:** the reference spec keeps this module's pages on the app's existing rails
feature (a per-page registry is given in §8). Recent related modules you may have built
(Bank Reconciliation, Cash Position, Expense Management) explicitly excluded rails — this one
does not have that instruction, so build it **with** rails per §8 by default. If that's wrong,
say so and it's a one-line change to exclude them instead.

## 0 · FIRST: remove the existing Vendor Centre feature entirely
Before building anything new:
- Locate every route, controller/handler, view/page, component, and nav entry for the
  current vendor feature: dashboard, directory index/create/edit/show, bills centre, payments
  centre, credits, statements, documents, evaluation, communication, aging, reports, settings.
- Locate its data model: does it have its own dedicated tables, or does it only reference
  shared data?
- **Dedicated-to-this-feature code and tables** (vendor directory records, vendor-specific
  evaluation/scorecard data, communication log, document metadata): remove/replace as part of
  this rebuild.
- **Shared services or data used by other modules** — the AP ledger/balances, bill
  approval/scheduling, payment processing/bulk payment/reversal, PO approval/conversion, GRN
  receiving, credit-note apply/reverse, GL posting handlers, tax settings, the General Ledger
  itself, banking, and the app's existing rails feature — do **not** delete these. Only remove
  the vendor-centre-specific code that *calls* them, then re-wire the new module to call the
  same shared services. If unsure whether something is dedicated or shared, check for other
  callers before deleting anything.
- Remove the old nav entry — the rebuilt module's nav entry replaces it, not sits alongside it.
- Confirm no other page, report, or feature links to the old feature's specific routes/views
  before deleting them; if something does, update that reference to point at the new module's
  equivalent screen.
- Clean removal, not a soft-hide — no dead code, unused routes, or orphaned views left behind.

Only proceed to the rebuild (§1 onward) once the old feature is fully removed and you've
confirmed nothing else in the app references it.

## 1 · Scope guard — do not touch anything else
- This affects only the Vendor Centre module's pages, styles, routes, and its own data. Do not
  touch any other module, except to re-wire calls to shared services as described in §0.
- Every button, drill-link, and report destination must be wired to a real, functioning
  route/handler — no dead links, no decorative buttons.
- No changes to bill approval/scheduling, payment processing/bulk payment/reversal, PO
  approval/conversion, GRN receiving, credit-note apply/reverse, posting handlers (AP/GL
  journals), or tax settings — this module surfaces and triggers these, it doesn't reimplement
  them.

## 2 · Functional/workflow rules to rebuild
- **Statuses** (pill + dot badges, exact colors in §3 CSS): `Active`, `Inactive`, `Overdue`,
  `Pending Approval`, `Unpaid`/`Partial`, `Paid`/`Posted`, `Reversed`, `Applied` (for credit
  notes), `Unapplied`. Confirm the actual transition rules used today before rebuilding, and
  preserve that logic, not just the visual badges.
- **Deactivate ≠ Delete**: deactivating a vendor preserves its history (existing rule); delete
  is blocked when transactions exist (existing rule) — surface that blocking message to the
  user rather than failing silently.
- **Vendor balances are always live, never duplicated**: Outstanding/Current/Overdue and every
  aging bucket must be computed from the real AP ledger and bill due dates at read time — never
  stored as a separate duplicate figure that could drift out of sync.
- **Credit-limit checks**: New Bill / Make Payment / New PO must prefill the vendor's terms,
  credit limit, bank details and tax info, and run the existing credit-limit check, warning
  when the limit is exceeded (existing rule — don't rebuild the check itself, just surface it).
- **Posted transactions are immutable**: corrections happen only via Reverse / Create
  Adjustment / Credit Note (existing handlers) — never allow direct editing of posted history.
- **Bulk actions** (directory multi-select: Export Selected / Deactivate / Delete; payments
  multi-select: Bulk Payment) call the existing bulk handlers — don't reimplement bulk logic,
  just wire the selection UI to it.
- **Search / filters / sort / pagination**: reuse the same query parameters and behavior the
  app already uses for list pages (status filter param, search param across
  code/name/contact/email, category filter, sort options) — keep state in URL params.
- **Document expiry reminders**: feed the app's existing notifications system if one exists;
  otherwise store reminder dates and render the amber "expires in {n}d" chip described in §3.

## 4 · Accessibility & responsive
- Status boxes (`.fbox`) use `aria-pressed`.
- Bulk selection bar uses `aria-live` so the "{n} selected" count is announced.
- Profile tabs use `role="tablist"`/`role="tab"` semantics.
- `⋯` more-menus use `aria-haspopup`.
- Breadcrumb uses proper `nav`/`a` semantics; focus rings use `--focus` (#94a3b8); table headers use `<th scope="col">`.
- Breakpoints (already encoded in the CSS in §3): `.statgrid` goes 3-col ≤1100px, 2-col
  ≤1000px KPI row / ≤768px statgrid; analytics row and report cards stack per their own
  breakpoints; tables scroll horizontally inside their cards. No horizontal page scrollbar at
  1280/1024/768.

## 5 · Integration rules (UI surfaces only — reuse existing handlers, don't rebuild)
- Vendor balances = live AP ledger balances; Outstanding/Current/Overdue computed from bill due
  dates; aging buckets from the same source — never stored duplicates (§2).
- New Bill / Make Payment / New PO prefill vendor terms, credit limit, bank, tax, and run the
  existing credit-limit check (warn when exceeded).
- Posted transactions are immutable — corrections via Reverse / Create Adjustment / Credit Note
  only.
- Document expiry reminders feed the app's existing notifications list if present; otherwise
  store reminder dates and show the amber chips from §3.3's Documents tab.
