# BUDGETING CENTRE — FULL REBUILD SPEC (design + functionality, "as designed in the mockup")

Rebuild Budgeting as the plan-vs-actual control centre: plan income and spending
by department/branch/project/cost-centre, approve and lock budgets, then compare
live actuals against them with variances, forecasts, adjustments and alerts —
replacing the existing, less-comprehensive Budgeting module. ALL DESIGN VALUES
BELOW ARE INLINE, EXTRACTED DIRECTLY FROM THE MOCKUP FILE. **Do not open, parse,
or infer from any mockup/HTML file — everything needed is already extracted into
this document.** No mockup dependency at build time.

---

## -1 · SCOPE DISCIPLINE (read first — this governs every phase below)

- Touch ONLY: the Budgeting module (its routes, controllers, views/components,
  its own migrations/tables, its module-menu entry, and the rails registry
  entries listed in §20 for its own pages).
- Do NOT touch, refactor, or "improve while you're in there": other modules
  (Sales, Purchasing, Banking, Payroll, Expenses, Fixed Assets), the rails
  feature's core implementation, the app-wide header/nav chrome, global CSS
  tokens/typography (already applied system-wide — reuse them, don't redefine
  them), GL posting/journal handlers, chart of accounts, tax handling,
  export/print/email handlers, or auth/permissions.
- Actuals are ALWAYS computed live from posted GL transactions — never stored
  or duplicated inside the budgeting module's own tables. If you find yourself
  about to add a column to cache an actual, stop — recompute it instead.
- Budgets never block posting by default. The spending-control hook (§19.3) is
  a listener on the EXISTING expense posting event — implemented without
  editing expense-module code. If achieving a warn/block hook seems to require
  modifying the expense module itself, STOP and report it rather than doing so.
- If implementing this module reveals a genuine need to change something
  outside this boundary, STOP and report it rather than modifying the shared
  component unilaterally.
- Create a dedicated branch (e.g. `feature/budgeting-rebuild`) before starting.
  Do not work on `main`/`master`.
- Work in phases in the order given. Commit after each phase with a message
  naming the phase. If a test suite exists, capture a baseline before §1
  (removal) and re-run after every subsequent phase — a new failure means STOP
  and report, not "fix around it."

## 0 · DISCOVERY — OLD MODULE (before removing anything)

0.1 Inventory the CURRENT Budgeting module in full: every route, controller,
    view/component, model, migration/table, menu entry, and any place other
    modules reference it.
0.2 Determine which of its database tables are **budget-specific** (safe to
    drop/replace — budgets, budget lines, budget templates, adjustments,
    alert rules) vs which are **shared tables** it merely reads from (chart of
    accounts, GL, departments, branches, cost centres, projects — never touch
    these).
0.3 If budget-specific tables already hold real data (existing budgets,
    approval history, adjustments), do NOT silently drop it — either write a
    migration that preserves/reshapes that data into the new schema, or
    clearly flag in your report what data would be lost and stop for
    confirmation before deleting.
0.4 Record this inventory in your final report (§24) as the "before" picture.

## 1 · REMOVAL — delete the old module

1.1 Remove the old module's routes, controllers, views/components, and menu
    entry.
1.2 Remove or migrate its budget-specific tables per §0.3 — never the shared
    tables identified in §0.2.
1.3 Remove any now-orphaned assets (old CSS/JS/blade partials) only used by
    the old module. Leave anything shared with other modules alone.
1.4 Confirm nothing else in the app still links to or depends on the removed
    routes/views before moving on — grep for the old route names.

## 2 · DISCOVERY — SHARED ENGINE (what the new module plugs into)

2.1 Locate: chart of accounts + account→category mapping, departments,
    branches, cost centres, projects, fiscal-year settings, GL posting events,
    the expense module's posting event specifically (needed for §19.3),
    notification channels (email/SMS/system), currency rates.
2.2 Locate user-preference storage (rail pin/expand prefs live there) and the
    header Favorites menu (rails feature — already implemented system-wide,
    per §-1 do not modify it).
2.3 Confirm whether an import handler (xlsx/csv) already exists anywhere in
    the app for reuse in §9's "Import from Excel" — if not, this module parses
    columns Category/Account/Annual itself (§9).

## 4 · STATUS BADGES + UTILIZATION THRESHOLDS — semantics

4.1 Badges (classes above): Draft = `.b-draft`; Pending Approval = `.b-pend`;
    Approved = `.b-act`; Locked = `.b-lock`; Over Budget = `.b-over`; Changes
    Requested = steel tint variant (rgba values in §3 comment).
4.2 Utilization bar (`.ubar`) thresholds, expense lines: ≤84% → `.u-ok`
    (teal); 85–99% → `.u-warn` (amber); ≥100% → `.u-bad` (red). **Income lines
    invert this meaning** — below target reads as amber/red, since under-target
    revenue is the problem, not over-target.
4.3 Variance chips (`.vchip`): `.ok`/`.warn`/`.bad` map to the same
    green/amber/red palette as the utilization bar.

## 19 · INTEGRATION & SPENDING CONTROLS

19.1 Actuals = live GL sums per mapped account/department/cost-centre/branch/
     project for the budget period; recompute on demand; **no stored actuals
     anywhere** in this module's tables.
19.2 Multi-currency: budget stores its own currency; cross-currency actuals
     convert at existing rate tables; reports show a conversion note.
19.3 **Spending control hook** (optional, per §7 settings): a listener on the
     EXISTING expense posting event — when a post would push a mapped line
     past the warn/exceed threshold, surface a dialog (warn: reason required
     to proceed; block: prevent with a message + "Request Adjustment"
     shortcut). Implemented WITHOUT editing expense-module code (per §-1).
19.4 Integrations are read-only from this module's perspective elsewhere:
     Payroll/Inventory/Sales/Purchasing postings flow into actuals
     automatically via the GL mapping — this module never writes to those
     modules' tables.
