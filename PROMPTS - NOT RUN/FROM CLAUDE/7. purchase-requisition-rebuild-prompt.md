# Purchase Requisition module — FULL REMOVAL of existing feature, then FULL REBUILD to exact design

## Objective
There is already a Purchase Requisition feature in the app today, but it is not
comprehensive/well-designed enough. You are to **remove that existing feature entirely
first** (§0), then **rebuild it from scratch** — List, Create, Edit, Detail, and Reports —
to match the exact markup/CSS given in §3 below, wired to real data and real workflow logic
(§2). This is not a re-skin of the current pages; treat it as tearing out the old
implementation and building a new one that happens to reuse the same underlying accounting
concepts (statuses, approvals, budget checks, PO conversion).

## 0 · FIRST: remove the existing Purchase Requisition feature entirely
Before building anything new:
- Locate every route, controller/handler, view/page, and nav entry for the current
  requisition feature: list, create, edit, detail/show, and any reports pages.
- Locate its data model: does it have its own dedicated tables, or does it only reference
  shared data (chart of accounts, suppliers, cost centres, budgets, GL/PO entities)?
- **Dedicated-to-this-feature code and tables** (requisition records, requisition line
  items, requisition-specific approval records): remove/replace as part of this rebuild.
- **Shared services or data used by other modules** (a general budget-checking service, the
  supplier registry, PO creation/posting logic, notification/audit-logging
  infrastructure, cost-centre data): do **not** delete these. Only remove the
  requisition-specific code that *calls* them, then re-wire the new module to call the same
  shared services. If you're not sure whether something is dedicated or shared, check for
  other callers before deleting anything.
- Remove the old nav entry — the new module's nav entry (§8) replaces it, not sits alongside it.
- Confirm no other page, report, or feature links to the old feature's specific routes/views
  before deleting them; if something does, update that reference to point at the new
  module's equivalent screen.
- Clean removal, not a soft-hide — no dead code, unused routes, or orphaned views left behind.

Only proceed to the rebuild (§1 onward) once the old feature is fully removed and you've
confirmed nothing else in the app references it.

## 1 · Scope guard — do not touch anything else
- This affects only the Purchase Requisition module's pages, styles, routes, and its own
  data. Do not touch any other module (Sales, Banking, other Purchasing pages, Reports
  outside this module), except to re-wire calls to shared services as described in §0.
- **This module is excluded from the system-wide rails feature.** Do not implement the
  slim rail / drawer / pin markup found in the design mockup (`.slim-rail`, `.ql-drawer`,
  `.rail-block`, `rail-pin`, the per-page "Quick Nav"/"Views"/"Reports" side lists, and their
  JS). The mockup includes this rail UI purely because it was built from the same template
  as other pages that *do* use rails — for this module, skip it entirely. No slim rail, no
  drawer, no pin, and the global "pin rails" preference has no effect on these pages. Rails
  on every other page in the app must remain exactly as they are today.
- Every button, drill-link, and report destination in the mockup must be wired to a real,
  functioning route/handler — no dead links, no decorative buttons.

## 2 · Functional/workflow requirements to rebuild (carry these over from the old feature's intent)
Even though the old code is being removed, the underlying business rules must still hold in
the new build:
- **Statuses**: `Draft`, `Pending`, `Approved`, `Rejected`, `Converted`, plus `Void` if that
  status already exists elsewhere in the app's data. Confirm the actual transition rules
  used today (submit, approve, reject, convert-to-PO, void) before rebuilding them, and
  preserve that logic, not just the visual badges.
  - Fix the mislabeled behavior where the list page heading currently reads "Create
    Requisition" — the rebuilt list page must read **"Purchase Requisitions"**.
- **Editing lock**: once a requisition's status reaches `Approved` or beyond, editing must be
  locked (read-only, with a visible notice) — preserve whatever lock rule already governs
  this today.
- **Approve/Reject visibility**: only shown when status is `Pending` **and** the current user
  is an approver for that requisition. Convert-to-PO is hidden once status is already
  `Converted`.
- **Budget check**: computed via the app's existing budget-checking logic/service (shared,
  per §0) — shows "—" until submit, then "Within budget" / "Over budget" once evaluated.
  Don't reimplement budget logic from scratch if a shared service already exists.
- **Convert to PO**: uses the app's existing PO-creation mechanism (shared, per §0) — the new
  Detail page's "Convert to PO" button must invoke it, not a new bespoke implementation.
- **Search / sort / pagination**: reuse the same query parameters and behavior the app
  already uses elsewhere for list pages (status filter param, requester/requisition-number
  search param, sort param, page param) so the URLs and filtering behavior stay consistent
  with the rest of the app.
- **Line item totals**: Subtotal / Est. Tax / Grand Total must always be visible on
  Create/Edit/Detail — never hidden even when all values are zero — and must be computed
  live as line items are added/edited (client-side recompute as you type, server-confirmed
  on save).
