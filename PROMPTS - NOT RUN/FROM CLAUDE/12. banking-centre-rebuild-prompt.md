# Banking Centre module — FULL REMOVAL of existing feature (except Cash Position & Bank Reconciliation), then FULL REBUILD to exact design, merged with those two already-built modules

## Objective
There is already a Banking Centre feature in the app today, but it is not comprehensive
enough. You are to **remove that existing feature entirely first** (§0) — **except** the
Cash Position and Bank Reconciliation modules, which are already built and must not be
touched — then **rebuild the rest from scratch** as the workspace for accounts, deposits,
withdrawals, transfers, cheque management and petty cash control, integrated with General
Ledger, Accounts Payable, Accounts Receivable, Payroll, Sales, Purchasing and Cash Flow so
every financial transaction updates the books. Match the exact markup/CSS given in §3 below,
wired to real data and real workflow logic (§2).

The rebuilt Banking Centre must **merge with, not duplicate**, the existing Cash Position and
Bank Reconciliation modules: every place this spec calls for a "Reconcile" action or a
Cash-Position/Bank-Reconciliation report link, it must open the real existing module, using
its real existing route. Do not rebuild their logic, pages, or calculations anywhere in this
module.

## 0 · FIRST: remove the existing Banking Centre feature — except Cash Position & Bank Reconciliation
Before building anything new:
- Locate every route, controller/handler, view/page, component, and nav entry for the current
  banking feature: dashboard, bank accounts index/create/edit/show, registers, transfers,
  deposits, cheques (issued + received), petty cash (funds + transactions), reports, settings.
- **Explicitly identify and set aside the Cash Position module and the Bank Reconciliation
  module** — their routes, views, controllers, and tables. These are **out of scope for
  removal and out of scope for rebuilding**. Do not delete, modify, or duplicate any part of
  them. Confirm their exact route names/paths during discovery — you will need them for the
  link-wiring in §3 and §8.
- For everything else in the banking feature (dashboard, accounts, registers, transfers,
  deposits, cheques, petty cash, the non-Cash-Position/non-Bank-Reconciliation report pages,
  settings): locate its data model — dedicated tables vs. shared data.
- **Dedicated-to-this-feature code and tables** (bank account records, transfer records,
  deposit records, cheque records, petty cash fund/transaction records): remove/replace as
  part of this rebuild.
- **Shared services or data used by other modules** — GL posting handlers, GL account
  mappings, approval workflow engine, tax settings, chart of accounts, currency rate tables,
  notification handlers, and the app's existing rails feature — do **not** delete these. Only
  remove the banking-specific code that *calls* them, then re-wire the new module to call the
  same shared services. If unsure whether something is dedicated or shared, check for other
  callers before deleting anything.
- Remove the old nav entry (for the parts being rebuilt) — the rebuilt module's nav entry
  replaces it, not sits alongside it. The Cash Position and Bank Reconciliation nav entries (if
  they have their own) are untouched.
- Confirm no other page, report, or feature links to the old feature's specific routes/views
  before deleting them; if something does, update that reference to point at the new module's
  equivalent screen. Any reference to Cash Position or Bank Reconciliation stays exactly as-is.
- Clean removal, not a soft-hide — no dead code, unused routes, or orphaned views left behind,
  for the parts actually being removed.

Only proceed to the rebuild (§1 onward) once the removal is complete and you've confirmed
Cash Position and Bank Reconciliation are fully intact and untouched.

## 2 · Functional/workflow rules to rebuild
- **Balances are always computed from posted ledger entries — never stored.** Account
  balances, running register balances, available funds, petty cash fund balances: all
  computed live at read time from posted transactions. No duplicate stored balance fields that
  could drift out of sync.
- **Status badges/type chips** (exact colors given in §3 CSS): Active/Posted/Cleared/
  Completed/Approved (mint), Pending Approval/Pending/Clearing (amber), Draft/On Hand
  (dark-tint), Issued/Transfer (steel), Cancelled/Reversed/Deactivated (gray),
  Outstanding/Overdue (red). Type chips: Deposit/Interest (green tint), Cheque/Withdrawal (red
  tint), Transfer (steel tint), Bank Charge (gray), Expense (red tint), Replenishment (green
  tint). Confirm the actual status transition rules used today before rebuilding, and preserve
  that logic — not just the visual badges.
- **Amount coloring**: credits/debits colored green/red in registers; balances bold; account
  type chips: Current gray, Savings teal tint, Mobile Money amber tint, Petty Cash gray, Cash
  steel.
- **Approvals & limits**: transfers above a threshold, and petty cash expenses above a
  custodian's limit, require approval via the existing approval-workflow handlers — surface
  the gate, don't reimplement it. Account access permissions and transaction limits (§4.3) are
  enforced on register/transaction actions via the existing rules.
- **Negative balances prevented**: per settings, warn or block negative bank balances via a
  listener on the existing posting handlers — don't build new posting logic.
- **Accounting entries** for each flow (reuse existing handlers, don't rebuild):
  - Transfer approval: DR to-account, CR from-account (+ charges → bank charges expense).
  - Deposit post: DR bank, CR source account (customer payment routes through the existing AR
    receipt handler where linked to a customer).
  - Issued cheque cleared: CR bank. Received cheque on hand: cheques-on-hand asset. Deposit of
    a received cheque: DR bank (clearing). Cleared/returned post their counterparts.
  - Petty cash approved expense: DR expense category, CR petty cash. Replenishment: DR petty
    cash, CR bank.
- **Search / filters / pagination**: reuse the same query parameters and behavior the app
  already uses for list pages — keep state in URL params.

## 4 · Accessibility & responsive
- Status boxes/tabs use `aria-pressed` where present.
- `⋯` more-menus use `aria-haspopup`.
- Focus rings use `--focus` (#94a3b8); table headers use `<th scope="col">`.
- Amount colors are always backed by text/signs (+/−), never color alone.
