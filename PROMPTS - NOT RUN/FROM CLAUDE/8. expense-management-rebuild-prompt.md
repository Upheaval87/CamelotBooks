# Expense Management module — FULL REMOVAL of existing feature, then FULL REBUILD to exact design

## Objective
There is already an Expense Management feature in the app today, but it is not comprehensive
enough. You are to **remove that existing feature entirely first** (§0), then **rebuild it
from scratch** — Dashboard, All Expenses, Record Expense, Detail, Expense Claim, Recurring
Expenses, Expense Categories, and Reports — as a proper transaction module: **Capture → Review
→ Approval → Posting → Payment/Reimbursement → General Ledger**. Match the exact markup/CSS
given in §3 below, wired to real data and real workflow logic (§2).

This is not a re-skin of the current pages; treat it as tearing out the old implementation and
building a new one that happens to reuse the same underlying accounting concepts (statuses,
approvals, GL posting, budgets, category mappings).

## 0 · FIRST: remove the existing Expense Management feature entirely
Before building anything new:
- Locate every route, controller/handler, view/page, component, and nav entry for the current
  expense feature: dashboard, list/index, create, edit, detail/show, post, claims
  (create/approve/reimburse), recurring, categories, reports, and any reverse/adjustment
  screens.
- Locate its data model: does it have its own dedicated tables, or does it only reference
  shared data?
- **Dedicated-to-this-feature code and tables** (expense records, expense allocation lines,
  expense-specific approval records, claim records): remove/replace as part of this rebuild.
- **Shared services or data used by other modules** — the journal/GL posting mechanism,
  the budget module (budget vs. used per category/cost centre), category→GL account
  mappings, the supplier registry, the employee registry, attachment storage, and the app's
  existing rails feature (§1) — do **not** delete these. Only remove the expense-specific
  code that *calls* them, then re-wire the new module to call the same shared
  services/components. If unsure whether something is dedicated or shared, check for other
  callers before deleting anything.
- Remove the old nav entry — the rebuilt module's nav entry replaces it, not sits alongside it.
- Confirm no other page, report, or feature links to the old feature's specific routes/views
  before deleting them; if something does, update that reference to point at the new module's
  equivalent screen.
- Clean removal, not a soft-hide — no dead code, unused routes, or orphaned views left behind.

Only proceed to the rebuild (§1 onward) once the old feature is fully removed and you've
confirmed nothing else in the app references it.

## 1 · Scope guard — do not touch anything else
- This affects only the Expense Management module's pages, styles, routes, and its own data.

## 2 · Functional/workflow rules to rebuild
- **Statuses** (pill + dot badges, exact colors in §3 CSS): `Draft`, `Submitted`, `Pending
  Approval`, `Approved`, `Rejected`, `Returned`, `Cancelled`, `Posted`, `Paid`/`Reimbursed`
  (Partially Reimbursed uses the amber variant). Confirm the actual transition rules used
  today before rebuilding them, and preserve that logic, not just the visual badges.
  - Fix the mislabeled list heading — it currently reads "Record Expense"; the rebuilt list
    page must read **"All Expenses"**.
- **Editing lock rules**, enforced in the UI:
  - `Draft` = fully editable.
  - `Submitted` = limited editing, or Return for Correction.
  - `Approved` = editing requires authorization (preserve whatever rule already governs this).
  - `Posted` / `Paid` = **no direct editing** — only Reverse or Create Adjustment. Surface a
    lock notice instead of editable fields.
- **Status-dependent row actions** on the All Expenses list (exact sets, don't mix them up):
  - `Draft` → Edit, Submit, Duplicate, Delete, Print.
  - `Pending Approval` → View, Approve, Reject, Return for Correction, Print.
  - `Approved` → View, Post, Edit (if authorized), Print.
  - `Posted` → View, Print, Download PDF, View Journal, View Payment, Duplicate, Reverse (danger), Audit Trail.
  - `Paid`/`Reimbursed` → View, Print, View Journal, View Payment, Reverse (danger).
- **Accounting Allocation**: multi-line allocation (account/department/cost-centre/amount),
  default account comes from the expense category's GL mapping. The allocation lines' total
  **must equal** the header total — validate this before save/submit, don't just display it.
- **"Expense ≠ payment"**: recording an expense never creates a payment. Payment/reimbursement
  only happens through the existing Record Payment action after posting.
- **Budget Control**: shows Annual Budget for the category / Used to date / This expense /
  Remaining after, computed via the app's existing budget module (shared, per §0) — don't
  reimplement budget math from scratch. Verdict chip: ✓ Within Budget (green), or ⚠ OVER
  BUDGET (amber, showing remaining/expense/over amounts) — going over budget requires
  additional authorization (a reason + an approver) before the expense can be submitted; gate
  submission on this, don't just display a warning.
- **Posting** (existing handler, reused not rebuilt) creates the journal entry: paid → DR
  expense / CR bank-cash; on credit → DR expense / CR Accounts Payable; reimbursement → DR
  expense / CR Employee Payable until reimbursed. "View Journal Entry" must link to the real
  posted entry.
- **Search / filters / pagination**: reuse the same query parameters and behavior the app
  already uses for list pages (status filter param, deep search param across expense
  number/description/payee/invoice number/employee/reference, category/department/payment-status
  filters, advanced filters panel, sort, page) — keep state in URL params.
- Never allow editing of a posted/paid transaction directly (§7.6 of the reference spec) — every
  reference in the Related Transactions chain is clickable, but editing only happens through
  Reverse or Create Adjustment.
