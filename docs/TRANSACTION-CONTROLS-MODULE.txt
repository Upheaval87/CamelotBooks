TRANSACTION CONTROLS MODULE (REVERSALS · UNPOSTED · AUTHORIZATION) — FULL IMPLEMENTATION SPEC
(AUTHORITATIVE MOCKUP HTML EMBEDDED IN APPENDIX A — do NOT read or depend on any external file.)

SCOPE:
Build a unified "Transaction Controls" workspace with three distinct operational panes:
1. Capture Reversal: Date-gated search of posted/saved transactions, detail view, and reversal capture workflow.
2. Unposted Transactions: Management of Draft/Finalized items (Reopen for edit or Delete).
3. Authorization: Approval queue for pending high-risk actions (Reversals, Reposts, Limit Overrides).

HARD GUARD — FRONTEND-ONLY VIEW LAYER: 
Do NOT modify existing Eloquent models, core business logic, or validation rules unless explicitly adding new columns/tables defined below. 
You are building the Blade/Livewire/Alpine view layer and wiring it to controllers/routes. NO NEW PACKAGES.

==================== 0 · DISCOVERY & ARCHITECTURE ====================
0.1 Locate existing `Journal`, `Deposit`, `Transfer` models and their status enums/constants.
0.2 Identify existing `User` model and permission structure (e.g., Spatie Permission or Gate policies).
0.3 Determine if an existing `AuditLog` service exists; if not, plan for standard Laravel logging.

==================== 1 · DESIGN TOKENS & ABSOLUTE RULES ====================
Tokens: Deep teal (#11454b, #0c3539), Sec (#128F8E, #149897), Mint (#7FD1C0).
R1 · ZERO BLUR: NO `backdrop-filter` on any scrim/modal. Use solid rgba tints.
R2 · CLEAN HEADER: The main page header is LIGHT (white/transparent bg), minimal typography, NO dark hero blocks, NO stat cards in the header.
R3 · TAB NAMING: The third tab MUST be labeled "Authorization" (singular).
R4 · DATE GATING: The Reversal list CANNOT load without a valid From/To date range. Validation: From <= To.
R5 · ACTION PLACEMENT: Lifecycle actions (Reverse, Reopen, Delete, Approve) exist ONLY inside modals, never as direct icons in the list rows (except View).
R6 · AUDIT TRAIL: All state changes (Reversed, Deleted, Authorized) must record User ID, Timestamp, and Reason/Comment.

==================== 2 · PAGE STRUCTURE ====================
2.1 HEADER: Simple `<h1>Transaction Controls</h1>` with a small icon tile. No subtitles, no stats.
2.2 NAVIGATION: Radio-button styled tabs for [Capture Reversal] | [Unposted Transactions] | [Authorization].
2.3 PANE 1: CAPTURE REVERSAL
     - Load Gate: Card with From/To dates, Presets (Today, Last 7d, Month), and "Load transactions" button.
     - Filters: Appears only after loading. Type, User, State, Search.
     - Datasheet: Paginated table of posted/reversed transactions. Columns: Ref, Type, Date, Desc, Amount, Posted By, Status, Action (View Only).
     - Empty State: Shown before initial load ("No period selected").
2.4 PANE 2: UNPOSTED TRANSACTIONS
     - List: Table of Draft/Finalized items. Columns: Ref, Type, Saved Date, Desc, Amount, Created By, State, Actions (View, Reopen/Delete).
     - Logic: Reopen converts Finalized -> Draft. Delete removes Draft permanently.
2.5 PANE 3: AUTHORIZATION
     - Queue: Table of Pending requests. Columns: Request Ref, Target, Type, Requester, Amount, Submitted, Waiting Time, Action (Review).
     - History: "Recently decided" section showing Approved/Rejected items.

==================== 3 · WORKFLOW DETAILS ====================
3.1 REVERSAL WORKFLOW:
     - User clicks View on a Posted transaction.
     - Modal shows lines + footer button "Reverse this transaction".
     - Clicking Reverse opens "Capture Reversal" modal: Warning panel, Mirrored Preview, Date Input, Auto-ref, Mandatory Reason, Submission Mode (Post Immediately / Submit for Auth / Save Draft).
     - Confirm Box: Stacked danger confirm.
     - Backend: Creates new Journal/Trans linked via `reversal_of_id`. Original marked `status=reversed`.
3.2 UNPOSTED WORKFLOW:
     - Reopen: Confirm box asks for reason. Updates status to Draft. Redirects user to source module edit screen (or stays in modal context if full-stack).
     - Delete: Danger confirm. Soft-delete or Hard-delete based on config. Audit logged.
3.3 AUTHORIZATION WORKFLOW:
     - Review Modal: Shows target details, impact preview, mandatory comment field for rejection.
     - Decision: Approve (Green) or Reject (Red). Both trigger stacked confirm boxes.
     - Backend: Updates `authorization_requests` status. If approved, executes the underlying action (e.g., posts the reversal journal).

==================== 4 · DATABASE SCHEMA ADDITIONS ====================
Table: `transactions_reversals` (or reuse journals with flags)
- `id`: bigint PK
- `original_transaction_type`: string (journal/deposit/transfer)
- `original_transaction_id`: bigint
- `reversal_transaction_id`: bigint (nullable until created)
- `reason`: text (required)
- `created_by`: fk users.id
- `approved_by`: fk users.id (nullable)
- `status`: enum(pending, approved, rejected, executed)
- `timestamps`

Table: `authorization_requests`
- `id`: bigint PK
- `request_type`: string (reversal, repost, limit_override)
- `target_entity_type`: string
- `target_entity_id`: bigint
- `requested_by`: fk users.id
- `authorized_by`: fk users.id (nullable)
- `amount`: decimal(15,2)
- `comment`: text (mandatory for reject)
- `status`: enum(pending, approved, rejected)
- `expires_at`: timestamp (optional SLA)
- `timestamps`

==================== 5 · SECURITY & PERMISSIONS ====================

- `viewReversals`: Requires 'finance.view' + 'audit.log.access'
- `captureReversal`: Requires 'finance.reverse'
- `manageUnposted`: Requires 'finance.create' OR owner check
- `authorizeRequests`: Requires 'finance.authorize' + Dual Control check (Requester != Authorizer)
